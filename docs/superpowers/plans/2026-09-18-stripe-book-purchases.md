# Stripe book purchases — feature plan

Status: implemented and verified locally on 2026-09-18. Production launch still requires a Stripe webhook signing secret and an intentional live Checkout/webhook smoke test. The user confirmed separate balances, a dismissible no-book-credit prompt when character credits remain, and disabled character navigation when both balances are exhausted.

## Intent and approach

Use Stripe-hosted Checkout for one-time purchases of one book credit plus five character-generation credits. A verified successful payment grants both balances atomically and upgrades the user to `basic`. Basic reading access does not expire when credits run out; generation requires funding of the corresponding type. Keep payment records separate from generation reservations so a later recurring product can grant allowances without changing the generation pipelines.

## Confirmed requirements

- Sell product `prod_VHc1FYY2QqVlJ0` through Checkout.
- Each purchase adds one book credit for later use, rather than purchasing a specific book.
- Each purchase also adds five character-generation credits. These use reservation, failure, and admin-release rules similar to book credits.
- Entering `/characters` with zero book credits and remaining character credits actively presents a purchase prompt, with an explicit option to continue to characters. When both balances are zero, disable the route and buttons/links leading there. Unfunded book generation remains blocked without book credits.
- Settings displays the current book-credit balance and provides payment options. Do not display a character-credit balance to ordinary users.
- With no available book credits, disable routes and buttons/links that start new book generation for non-admin users. Admins are exempt. Preserve the agreed trial entitlement and existing funded-retry rules.
- The first successful purchase ends trial restrictions and grants Basic access without an expiration date.
- Users pay for further books individually.
- Existing credentials are named `stripe.account`, `stripe.secret`, and `stripe.publishable`.
- Recurring subscriptions with a different Stripe product and periodic book allowances are a later feature.

## Product rules

- Retain the existing Basic maximum of 10 pages; trial books remain capped at 5 pages.
- Sell exactly one credit per Checkout session initially. Credits do not expire.
- Basic users with zero credits retain access to all existing books, including trial books. Only new generation requires a purchase.
- Upgrade ends unused trial allowance. Existing books with held trial reservations keep their original funding and can finish or retry without spending a purchased credit. A released trial reservation does not fund another generation after upgrade.
- Reserve a purchased credit before enqueueing a new book. Keep it assigned through generation failure, completion, illustration retries, and admin reruns of that funded book.
- Return the reservation on initial queue handoff failure. An admin may return it for a failed book, provided no generation/retry is active. A released book must acquire funding again before further generation.
- Illustration retries retain existing per-illustration limits and admin overrides; automatic retries add no credit cost.
- Deleting a funded book does not return its credit. Preserve the financial/reservation audit record.
- Handle cash refunds and disputes manually through Stripe initially; automatic changes to credits or Basic status after reversals require a separate agreed policy. Admin credit release is not a cash refund.

### Character-credit lifecycle

- Grant exactly five credits per paid purchase; each credit can fund one distinct character-image generation request. Character credits do not expire. Returning a book reservation does not grant another five character credits; the bundle is granted only by payment fulfillment.
- Reserve a credit atomically when accepting a new Basic character-image request, before screening or generation is queued. Repeated submissions of the same request, cached completed-image reuse, and metadata changes that do not generate a new image do not spend another credit.
- Screening itself does not consume a separate credit. Return the reservation if screening definitively rejects the input before generation, or if initial queue handoff fails. Keep it held during screening review/unavailability so the pending request remains funded; admins can release it before further processing. A released request must reacquire credit before generation.
- Generation failure, provider refusal after generation starts, or an unknown provider outcome retains the reservation for admin review. Automatic retries and admin retries reuse existing funding. Keep the existing explicit confirmation for retrying an unknown outcome.
- Admin release records actor/reason and is blocked while a worker or retry can still consume the reservation. Released requests cannot be resumed by stale jobs without reacquiring funding. Deletion must preserve the credit audit trail and must not automatically refund completed generation.
- Preserve trial character rules: currently three generations per character and 24 per trial user. For Basic, replace the account-wide 24-generation ceiling with purchased character credits; retain the per-character limit and its admin override. Otherwise additional purchases would stop working after 24 generations.
- Snapshot trial funding for character requests accepted before upgrade so asynchronous approval/generation does not unexpectedly consume a newly purchased credit.

### Purchase modal and Settings

- Use one shared purchase modal with advisory and blocking variants. Enforce actual funding restrictions server-side for direct requests, Turbo requests, forms, and JSON; navigation interception alone is insufficient. Blocked JSON requests receive `402 Payment Required` with a payment-options URL. A lack of book credits alone must not reject a character request with valid character funding.
- **Confirmed:** check the two balances separately. On each fresh navigation into `/characters` with no book credits but remaining character credits, show **You are out of book credits** and actively offer **Buy book credit** / **Continue to characters**. Continuing grants access to the requested character page; it does not add credits or bypass character-generation funding. Do not immediately re-open the prompt after Continue or after a successful character submission; show it again on a subsequent fresh entry. Direct HTML/Turbo navigation gets the same advisory experience.
- When both available balances are zero, disable every user-facing button/link into `/characters` or new-character creation, including mobile navigation, with accessible disabled semantics and an explanation directing users to Settings. Prevent keyboard activation as well as mouse clicks. Direct URLs and stale enabled links must still be blocked server-side and present the purchase options through Settings; there is no Continue option in this state.

| Available book credits | Available character credits | Character navigation behavior |
| --- | --- | --- |
| More than zero | More than zero | Allow normally. |
| Zero | More than zero | Prompt about exhausted book credits; allow Continue to characters. |
| More than zero | Zero | Retain the character-credit purchase gate; existing characters remain usable in funded books. |
| Zero | Zero | Disable navigation buttons/links and block direct entry; payment options remain accessible in Settings. |

- Existing funded work, completion callbacks, and eligible retries use their held reservation even if the unreserved balance is zero. Selecting already-generated characters for a funded book does not spend character credits. Book library/reading routes remain accessible to Basic users with no credits.
- Book generation has a hard gate when no book credit is available: disable new-book/generate buttons and links across desktop/mobile views, and deny direct navigation or submissions that would start unfunded generation. Include `/books/new`, create, and updates that start unfunded generation; a hidden or disabled button alone is insufficient. Stale links/direct HTML or Turbo requests show payment options without starting work; blocked JSON receives `402 Payment Required`. Admins bypass both the UI gate and server-side funding requirement, even at zero balance. This does not override the separate character-credit rules or interrupt already-funded work.
- Trial users retain existing free entitlements until exhausted or expired; requiring purchased balances during an active trial would prevent the trial from working. Admins bypass user purchase modals.
- The modal offers **Buy book credit**, explaining that it includes five character generations, and links to payment options in Settings. Show **Subscriptions coming soon** as an unavailable option until recurring billing exists; do not provide a working Subscribe action for an unimplemented product.
- For the advisory variant, Continue opens characters despite the zero book balance. For a blocking variant, a Basic user can dismiss the modal and return to reading; dismissal does not unlock the blocked route. Expired trial users remain restricted to Settings/payment/auth and see the existing required-payment modal with a working purchase action.
- Settings shows current available book credits, updates after verified payment, reservation, or release through the existing Turbo facilities, and reconciles on reload. Keep character balances out of the user UI; a depleted-character message can explain that buying a book credit replenishes character generation without displaying a count. Admins can inspect both balances.

## Scope boundaries

In scope: Checkout, server-controlled pricing, verified payment fulfillment, Basic upgrade, durable book and character credits/reservations, shared purchase modal, Settings book-balance/payment/history UI, expired-trial payment access, admin balance/failure visibility, tests, and deployment instructions.

Out of scope: recurring billing, periodic allowance grants, configurable bundles or bulk purchases, coupons, a customer billing portal, automatic cash refunds/dispute entitlement changes, a new tax calculation feature, historical usage reconstruction, and unrelated generation changes. The fixed one-book/five-character bundle is included. Existing Stripe price/tax configuration must be checked before launch.

## Repository findings and architecture

- `User#paid?` currently treats every non-free tier as paid. `TrialBookReservation.reserve_for!` skips paid users, so changing `tier` alone would grant unlimited generation. Add explicit Basic credit enforcement across every generation entry point.
- `Book::TIER_LIMITS` already defines Basic as 10 pages. Preserve it unless the product decision changes.
- `Book` owns reservation, enqueue, rerun, completion, and illustration retry coordination. Extract a focused `BookFunding` service to select existing funding first, then acquire trial funding or a purchased credit. Preserve the current locks and commit-before-enqueue behavior.
- Keep existing `TrialBookReservation` data and rules. Add `BookPurchase` for a local order and its Stripe Checkout/payment identifiers, expected product/price/amount/currency, status, and paid timestamp.
- Add one `BookCredit` per fulfilled purchase, enforced by a unique purchase reference. Add `BookCreditReservation` records with credit/user/book references, held/released state, release actor, reason, and timestamp. Unique held-credit and held-book indexes prevent double spending; released history remains auditable. Book deletion nullifies the book reference without making the credit available.
- Add five `CharacterCredit` records per purchase with unique `(purchase_id, ordinal)` values 1–5. Add `CharacterCreditReservation` with credit/user/request references and equivalent release audit fields; unique held-credit and held-request indexes prevent duplicate charges. Keep paid character funding in a focused `CharacterFunding` service integrated with `CharacterImageRequest`, assessment notifications, `GenerateCharacterImageJob`, recovery, and admin retries. Use the existing user-first lock order; commit before enqueueing and preserve fingerprint deduplication.
- Persist processed Stripe event identifiers with database uniqueness. Apply fulfillment, one book credit, five character credits, and Basic upgrade atomically; also enforce uniqueness by Checkout session and purchase so different events cannot grant the same bundle twice.
- Keep Stripe operations in `Payments::Checkout` and `Payments::FulfillCheckout`. A narrow webhook controller verifies raw-body signatures independently of browser authentication, trial gating, tutorial redirects, and browser checks. Only that endpoint is exempt from CSRF.
- Browser payment routes remain authenticated and owner-scoped, but accessible to expired trial users. Keep CSRF on purchase creation. Settings, success, and cancellation views show pending/paid/failed states without granting access from redirect parameters.
- Retain trial/paid failure snapshots and add funding source/reservation/purchase references when available, so an upgrade does not obscure how a failed book was funded.

## Validation and risks

- **Book generation gate:** zero book credits disables every new-generation control and blocks direct GET/POST/PATCH requests for unfunded generation; admins can use the same routes and controls at zero balance. Verify desktop/mobile and keyboard behavior, stale links, funded retries, trial slots, and continued reading/Settings access.
- **Payment integrity:** duplicate/concurrent webhook deliveries, different events for the same purchase, delayed payment, unpaid completion, forged/foreign success URLs, wrong product/price/quantity/currency/environment, invalid signature, out-of-order events, and failure between Stripe success and local persistence.
- **Purchase initiation:** double-clicks, retries after API timeout, cancellation followed by a new purchase, changed default price, and missing/inactive/recurring prices. A canceled browser redirect is not evidence that payment can never succeed.
- **Entitlement integrity:** first purchase before or after trial expiry, upgrades during generation, zero-balance reading access, two books competing for one credit, repeated completion callbacks, deleting books, stale generation jobs, admin release racing with retries, and existing trial-funded books surviving upgrade.
- **Character integrity and UX:** exactly five character credits per unique payment; no extra credits on book release; concurrent character submissions competing for the last credit; duplicate/cached requests; rejection before generation versus provider failure; stale approvals/jobs after release; trial requests completing after upgrade; purchases beyond the old 24-generation ceiling; all four book/character balance combinations; advisory prompt on fresh entry with a working Continue action and no immediate re-prompt; disabled buttons/links and server-side denial when both balances are zero; stale navigation after balance changes; modal behavior for direct HTML/Turbo/JSON requests; funded retries at zero balance; Settings live book balance with no user-visible character count.
- **Operational checks:** no secret values in logs or fixtures; Stripe test credentials and a test product/price for local smoke tests; webhook failures visible and replayable. The provided live product has not yet been inspected through the Stripe account.
- **Approved defaults:** retain the existing 10-page Basic limit; end unused trial allowance on upgrade; keep refund/dispute entitlement changes manual for this first version; check book and character balances separately. Character lifecycle details above extend the approved book reservation behavior. Tax setup, actual price/currency, and the webhook signing secret remain launch configuration dependencies.
