# Rails 8 defaults: Kamal, SQLite, and Solid adapters

Status: implemented and verified locally; real deployment awaits infrastructure values.
Date: 2026-09-10
Requested planning skill: `create-plan`.

Implementation notes: the final comparison uses Rails 8.1.3.1, the latest stable
release on this date. Development data import was skipped because preserving the
relational graph, IDs, sequences, JSON values, and upload references safely would
exceed the approved single-migration bound. The legacy PostgreSQL volumes remain
untouched. MinIO remains the production upload store, so the Kamal volume contains
the four SQLite databases rather than Active Storage objects.

## Intent and approach

Move the existing Rails application toward the infrastructure generated by a default Rails 8 application: Kamal deployment, SQLite, Solid Queue for Active Job, Solid Cache for Rails.cache, and Solid Cable for Action Cable. Target a single production host with persistent local storage, four separate production SQLite databases, Thruster, and Solid Queue supervised through Puma. Preserve application functionality and existing image-generation safeguards. Compare against the latest stable Rails generator while retaining compatibility with the installed Rails 8.0 release; do not upgrade Rails merely to accomplish this migration.

## User decisions and scope

- There is no production database to migrate. Production starts with empty databases.
- Development data preservation is optional. Attempt it only if it fits in **one new migration strictly under 200 lines**, with no edits to existing migrations required for the data transfer. Do not hide additional transfer logic in helper files to evade this limit.
- If that bounded transfer is impractical, skip it and initialize fresh SQLite development databases. Report the decision; no further permission is needed to skip preservation.
- Schema compatibility changes necessary for SQLite are separate from optional data transfer. Keep those changes minimal and explain any historical migration edits required for clean SQLite initialization.
- Preserve PostgreSQL Docker volumes and source data, even if data transfer is skipped. Do not drop or recreate those databases.
- In scope: database dependencies/configuration/schema compatibility, optional bounded development import, Solid configuration and worker startup, Kamal/Docker configuration, tests, and development/deployment documentation.
- Out of scope: production data transfer, frontend redesign, unrelated cleanup, Rails version upgrades, changing object-storage providers, multi-host SQLite deployment, and introducing another job system.
- This handoff authorizes implementation preparation. Actual deployment requires real server/domain/registry details and an available authorized destination; do not invent them or claim deployment from a local smoke test.

## Current repository findings

Recheck these during implementation because the workspace contains substantial existing modified and untracked application work. Preserve that work; do not reset it or assume HEAD represents the intended application.

- `Gemfile` specifies Rails `~> 8.0.2`, PostgreSQL, all three Solid gems, Thruster, and Mission Control Jobs. Kamal configuration exists but uses placeholder infrastructure values.
- `config/database.yml` uses PostgreSQL in every environment, separate development/test queue databases, and production database URLs. Production cache shares the queue URL; Cable writes to the queue database.
- `config/queue.yml` is present, alongside an inconsistent `config/solid_queue.yml`; establish actual readers before removing obsolete configuration.
- `config/puma.rb` already enables the Solid Queue plugin when `SOLID_QUEUE_IN_PUMA` is set. `Procfile.dev` currently lists web, JS, and CSS only.
- `config/deploy.yml` already contains `SOLID_QUEUE_IN_PUMA` and a persistent `/rails/storage` volume, but server/domain/image/registry values are placeholders.
- `db/schema.rb` contains PostgreSQL extensions, `jsonb` columns, a PostgreSQL `roles` array, and Solid tables. `db/queue_schema.rb` also includes application tables. Other Solid schema files and migrations exist; audit ownership before regenerating anything.
- `Dockerfile` installs PostgreSQL dependencies and has the final runtime stage/non-root setup commented out. Preserve ImageMagick and other native dependencies actually required by the app.
- `bin/docker-entrypoint` checks for a direct Rails server command, whereas the Docker command starts through Thruster. Fix startup database preparation for the actual command shape.
- Production uses MinIO for Active Storage; CarrierWave also exists. Preserve upload configuration and references.
- Recurring recovery jobs and paid generation reservations already exist. Restart/retry behavior must not cause duplicate paid API calls.

Remove obsolete PostgreSQL environment-variable requirements and guard against an inherited `DATABASE_URL` overriding SQLite.

4. [x] **Normalize Solid ownership and worker execution.** Reconcile duplicated/misplaced Solid tables and schema files without deleting source PostgreSQL data. Configure production Queue, Cache, and Cable against their own databases. Keep `config/queue.yml` and `config/recurring.yml` authoritative. ## Validation checklist and risks

- [x] Before the switch, establish the baseline with `docker compose up -d test_db test_worker_db`, `bin/rails db:prepare RAILS_ENV=test`, and `bin/rails test`, all from WSL.
- [x] After schema changes, run `bin/rails db:migrate` and `bin/rails db:prepare RAILS_ENV=test` from WSL; restart running Rails/workers. A fresh-install path must prepare all four production databases too.
- [x] Development, test, and production never share SQLite files. Tests cannot write to the PostgreSQL source or development SQLite data.
- [x] JSON/array defaults, roles, associations, uniqueness, and future inserted IDs retain their semantics.
- [x] SQLite serializes writes and does not reproduce PostgreSQL row locks. Prove reservation/claim behavior under contention and bounded busy handling; do not assume existing `with_lock` behavior alone proves duplicate-request protection.
- [x] Database transactions do not become atomic across separate primary/queue files. Review enqueue-after-commit behavior and recovery when queue insertion fails.
- [x] Long-running external API calls do not hold avoidable SQLite write transactions. Unknown paid outcomes remain unknown instead of being automatically resent.
- [x] Queue retries, scheduled recovery, job restart, cache, and broadcasts work with real production adapters in addition to unit-test adapters.
- [x] SQLite backups are consistent with WAL operation; document a supported backup procedure rather than copying only a live main database file. Restore is tested using disposable data.
- [x] Container redeployment preserves database files, permissions, and local uploads. A code rollback does not automatically reverse schema or newly written data.
- [x] Full Rails suite passes before handing off any implementation code. No full test run is needed solely for writing this plan.
